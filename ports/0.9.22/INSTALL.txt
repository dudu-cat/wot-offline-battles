World of Tanks 0.9.22.0.1 #1513 LAN/offline package 0.3.76
================================================================

This folder is directly mergeable into the frozen Chinese HD client root.
It supports standard battles only and always uses the matching Python 3 LAN
server, including when there is only one player.

If you received the ZIP form, extract its contents directly into the game
root. The archive itself contains `mods` and `INSTALL.txt`; it does not add an
extra wrapper directory.

Use `ports/0.9.22/server/lan_battle_server.py` from the same repository
checkpoint as this package.
The v5 message schema is round-scoped and stricter than older v5 packages, so
mixing an old client and new server (or the reverse) is unsupported.
This #1513 client identifies its build during the LAN handshake. The first
client pins an empty server room to one build; a legacy 0.8.2 client cannot join
that room because its map and coordinate contracts are different. Use another
server port for a simultaneous 0.8.2 room.

Version 0.3.76 keeps the gun, stock reticle and optional server marker frozen
through PREBATTLE after one initial alignment. Stock aiming starts at the one
native BATTLE transition; movement and fire unlock at the same boundary.

Neutral coast drag now uses a conservative 0.65 share of recovered track grip,
up from 0.55. The exact client supplies mass, speed and terrain data, but its
native C++ W-release curve cannot be recovered statically, so retail identity
is not claimed. Verify Type 62 stopping feel in Windows #1513.

Version 0.3.75 starts the exact native VehicleGunRotator during PREBATTLE after
publishing its targeting parameters. It temporarily admits only the rotator's
PlayerAvatar.isOnArena guard and restores that flag immediately. The reticle
and physical turret should therefore follow the same direction throughout the
countdown; movement and firing still unlock only at BATTLE.

Shared strategic route searches now prefer baked cells with more proved exits
and preserve that clearance through smoothing. This can keep Lakeville's
narrow-road traffic nearer the usable centre, but it does not add graph links
or relax collision, water, grade or one-cell-passage checks. Full-pair Bot
observations now run every 0.40 seconds; periodic lane refreshes occupy the
final 0.20 seconds and ordinary pairs beyond 585 m skip their native lane ray.
The selected target still passes a separate lane check no older than 0.20
seconds before any shot.

Bots now carry finite ammunition using the installed gun's real capacity.
Available standard, higher-penetration and HE categories use a 3:2:1 baseline;
SPGs use an HE-led 1:1:4 baseline. Missing categories are redistributed. The
server plans standard ammunition normally, HE for a safely fragile or
finishable target, and a higher-penetration round when standard penetration is
inadequate. Human armor/class input is derived from the installed descriptor
and cached by vehicle name rather than accepted from a mutable live player
record. The current and next rounds are fixed separately: a planned round loads
only after the copied reload state becomes ready, and the actual fired round is
the one decremented. The server validates the atomic inventory, loaded/next
transition and one-round fire decrement, and preserves them across authority
takeover. Player ammunition admission remains client-owned.

Lakeville still has one exact CTF objective per team, but its compiled space
also contains assault2 base visuals under another visibility bit. Exact #1513
can briefly replace the selected CTF bit with its full server mask late in
startup. Version 0.3.75 reapplies CTF bit 1 after deferred client readiness so
the assault2 instance stays hidden. It does not modify XML, capture rules,
minimap or team assignment. Verify countdown gun tracking, narrow-road traffic,
sustained frame pacing, Lakeville base visibility and Bot ammunition behavior
in Windows #1513.

Version 0.3.74 reduces repeated authority-client work while preserving local
simulation state. BotRuntime keeps the complete local Bot records needed by

LANClient.send_bot_state crosses the v5 wire boundary does it copy the fields

sample may carry the previous exact 3x3 receipt only when the receipt's own

Version 0.3.72 gives every player and authority-Bot shell real flight time.
The gravity path is checked in collision chords no longer than 25 ms, including
the target vehicle's movement during each interval. Targets may therefore move
clear after launch, and firing at a moving vehicle requires lead rather than an
instant fire-time hit test. The server retains accepted launches and progress
in a durable round ledger, carries active shots across shooter disconnects and
authority takeover, and atomically commits terminal direct/splash damage plus
shot-destructible receipts.

SPGs retain their stable rear deploy point and can fire exact low- or high-arc
solutions. The client schedules arc collision work fairly with a hard budget of
four native rays per rendered frame. A moving-target solution is frozen once it
enters exact launch proof, so target updates cannot continually restart that
work. If the completed path is more than 1.5 m from the target's projected
impact pose, the exact receipt may wait only while that same target and 3-D
velocity will cross its endpoint; this is rechecked every frame. Otherwise it
is rejected and re-led before firing, and the total proof lifecycle is bounded
to 120 seconds. The exact #1513 catalog's
longest reachable grounded case is 5.872907831 seconds (FV3805, 440 m/s,
146 m/s2, 70-degree high arc over the baked maps' 89.106 m maximum terrain
drop); ordinary low arcs are substantially shorter. Stun is still disabled
because there is no complete
canonical penalty/duration and medical-kit recovery loop. On Windows #1513,
verify tracer appearance, shell timing and dodgeability, low/high artillery
selection, sustained frame pacing and repeated-round cleanup.

Version 0.3.71 moves ordinary LAN serialization and socket writes off the game
thread. Each plain-JSON message is frozen and appended to a bounded reliable
FIFO without coalescing. The hello remains the synchronous first wire message;
a single sender drains later messages in order. Restart generations are
isolated. Invalid payloads are rejected before admission; queue overflow or
sender failure disconnects instead of silently dropping ordered state.

A support ray that jumps above the bounded climb/step limit now restores only
the current movement tick, so a player or Bot is not lifted onto a wagon, roof
or large prop. Hard contact and realised rollback clear the affected Bot's
decision and motion proof, retain one finite escape side and force a replan.
Bots align before driving onto a meaningful ascent. Route smoothing, live reach,
lookahead and partial-path continuation keep the turn immediately before a
climb rather than replacing it with an uncontrollable diagonal shortcut.

This package does not include the 0.8.2 native WGVehicleFilter/physics
experiment. Artillery still has only the existing rear-anchor deploy/hold
behavior: there is no open-sky proof, ballistic arc, indirect-hit solver or
stun loop. Verify these movement and contact changes, camera switching and

Version 0.3.70 treats a continuous bounded uphill or downhill ground profile as
drivable only when the actual hit surface is ground-like. Neutral coasting
keeps the established flat-road drivetrain drag. While the current motion is
downhill, that drivetrain share is progressively unloaded with grade; at or
beyond the static-hold tangent only descriptor rolling resistance remains.
Uphill coasting receives no downhill relief. Opposite throttle, handbrake and
the static hold are unchanged, and flat/raised walls plus sharp steps still
block.

At physical speed, crushing still requires exact swept-OBB contact and the
unchanged stock mass/speed/health kinetic gate. An accepted fragile/module
continues without the hard-wall speed impulse. At low speed or from rest, an
active drive command may use forward/reverse descriptor top speed only as a
stock-gate proof. It may submit native destruction only when the exact leading
hull face, a 0.075-m contact margin and this frame's real physical travel reach
the item. The submission holds the pose for that tick and restores the real
pre-step speed; the top-speed proof is never copied into vehicle, network or ram
state. On later ticks, a pending native skin is skipped only to its exact
registered OBB exit and then recast. Falling objects, backing walls,
expired-but-still-solid skins and unknown geometry remain blocking.

Authority Bots retain the existing staggered driver cadence and 15/20-metre
three-lane corridor. A catalog item can be planned through only after a read-
only exact-OBB classification proves it stock-crushable; planning never
destroys. Planner alternatives keep their existing six horizontal rays. Only
the finally selected flat, straight, powered motion sample casts the additional
nine exact hull rays: three commit-width lanes at all three commit heights over
15 metres. The typed receipt records origin, yaw and forward/reverse direction.
The per-render world pass may be reused only when actual-frame travel keeps the
current leading-hull sweep strictly inside that proof and no catalog item
touches the hull. A hard receipt blocks immediately; a deferred receipt is not
cached. Missing/stale proof, pose/yaw drift, catalog contact, coasting, braking,
turning or airborne motion falls back to world-first checking. At most 13 final-
motion receipts run per render frame. The waiting rotation retains only Bots
that actually made this eligible request; idle, hard-blocked, turning or
airborne Bots drop out. Unattempted receiptless work keeps initial-backlog
priority over refreshes. Once its native callback itself defers, it loses that
priority and rotates behind the other enrolled requests, so neither a persistent
callback deferral nor a refresh can starve the other. A deferred eligible Bot
pauses for that frame at pre-step real speed, does not enter route-failure
recovery and neither caches the deferred result nor substitutes a per-frame
world sweep. Initial deadlines span the full
0.0975-second decision interval. At a strict simulated 24 FPS, 29 startup
receipts drain as 13/13/3 jobs and 13/26/29 cached proofs; Windows #1513 remains
the frame-time acceptance boundary. The low-rate stationary
scan only registers nearby streamed chunks so a Bot stopped at a fence can
reach the exact contact path. One ray may skip at most four proved soft items
through their exact exits; a fifth fails closed and remains a Windows #1513

Player shells use the native material identity first. Anonymous slots fall
back only to the nearest unique catalog OBB before the first static collision
or vehicle, so ambiguity and wall/vehicle occlusion fail closed. Shot damage

past a thick object.

The exact #1513 `destructibles.xml` sets
`maxHpForShootingThrough=19`. Every material has
`projectilePiercingPowerReduction=(0, 25)`, so AP, APCR and APHE may continue
through a scale-adjusted item with at most 19 HP, keep the same damage and lose
a fixed 25 mm of penetration per item. Loss is cumulative. The first operation
that needs a penetration test lazily samples one factor and reuses it while
evaluating the range-dependent mean at each tested item and the eventual
vehicle. A pure miss or HE/HEAT stopped at a destructible does not consume
penetration RNG. If less than 1 mm remains at an item, the shell
disappears there. Old #1513 HE and HEAT stop at the first destructible, with HE
exploding there. A destructible above 19 scaled HP can break but still stops the
shell.

Those numeric values are exact pinned-build data. Shell-family outcomes and
cumulative, damage-preserving traversal are supported by official same-family
descriptions, but the private 0.9.22 retail server's exact operation order is
not public. This package's lazy range/RNG/reduction order is an explicit
high-confidence reconstruction, not a source-identical claim. Shot damage keeps
the encoded effect/replay bit, but the local manager order is not queued for
projectile synchronization: this copied projectile path has no later #1513
`damagedDestructibles` payload to release that queue.

Install
-------

1. Close the game.
2. Delete older `org.peng.offline_lan_0922_*.wotmod` files from:

       <game root>\mods\0.9.22.0.1\

   The old loader scans every package, so leaving an incompatible package next
   to the new one can still stop startup.
3. Copy this folder's `mods` directory into the game root.
4. Confirm this file exists:

       <game root>\mods\0.9.22.0.1\org.peng.offline_lan_0922_0.3.76.wotmod

5. This copy-ready package includes:

       <game root>\mods\configs\offline_lan_0922\config.json

   It is preconfigured for the server address shown in that file. You can also
   change the address in the native LAN settings window described below.
   The same config directory contains validated `navgraphs`, `foliage` and
   `destructibles` batches for all 41 supported maps; keep all three
   directories intact.

Start the server
----------------

From the repository on the Mac host, run:

    python3 ports/0.9.22/server/lan_battle_server.py --host 0.0.0.0 --port 28782 --map server_random

Allow inbound TCP port 28782 through the host firewall when another computer
or virtual machine connects.

Start a battle
--------------

1. Leave the server terminal open.
2. Start `WorldOfTanks.exe` without logging into an online account.
3. On a fresh profile, accept the stock EULA once. Its version is stored in
   `mods\configs\offline_lan_0922\account_state.json` for later launches.
4. Select the tank you want to use, then click the hangar's native Battle!
   button to join the LAN waiting room. The current tank and its descriptor
   health are sent to the LAN server; there is no silent MS-1 fallback. If no
   valid tank is selected, the client stays in the hangar and shows a warning.
   This does not use retail matchmaking or the retail training-room service.
5. If the endpoint cannot be reached, the stock settings window opens
   automatically while retrying. Its Description field contains
   `LAN SERVER: host:port`; edit it if the server address changed. Before a
   welcome, this settings surface does not grant room-host authority. You can
   also click Battle! again while connecting to open it explicitly.
6. The first waiting player becomes room host and receives the stock training
   settings window as a map picker. Its Description field shows the endpoint,
   live player list and `CREATE = START BATTLE FOR EVERYONE`; the host may edit
   the endpoint on the first line and save it there.
7. Every later player clicks the same Battle! button and waits in the hangar.
   Only the host can choose a standard (`ctf`) map and use the window's primary
   action. The server broadcasts that one selected map to every waiting client.
   There is no F12 or `0` key workflow.
   Closing the host picker leaves it closed; the host clicks Battle! to reopen
   it.
8. The server starts the selected map and fills both teams to 15 vehicles.
   The shared 15-second prebattle countdown runs after every human vehicle has
   loaded and the authority has published the bot line-up. Bots continue to
   appear during that countdown, matching the 0.8.2 battle flow. Player
   movement and shooting unlock only when it reaches battle. The server sends
   one ordered tick-zero barrier before snapshots; each client projects its
   relative timing from the network receive timestamp on a monotonic clock.
   The battle debug panel then shows the LAN socket RTT rather than
   retail-server ping.

After a team is eliminated, the battle freezes and returns all connected
players to the waiting room after five seconds. The current host receives the
map picker again. If the host leaves while waiting, ownership and the picker
move to the lowest connected player id. New connections are rejected while a
round is active and may join after the room returns to waiting.

Troubleshooting
---------------

- `unsupported compression type`: an older or incorrectly compressed wotmod
  is still present. Keep only the 0.3.76 package; its members use Store method.
- No connection in the server terminal: check `config.json`, the host LAN IP,
  virtual-machine network mode and TCP 28782 firewall access. A failed attempt
  automatically opens the native endpoint editor; Battle! can reopen it.
- `SOUND_ERROR` event `2967843034` is `hangar_v2_music_lobby`, not a gun
  event. Record whether lobby music is actually missing after a normal battle
  return; a firing-audio problem needs the event ID logged at the shot time.
- A traceback appears: close the client and keep `python.log`; it identifies the
  exact remaining client API boundary. This package does not create separate
  probe or trace files.

Current boundary
----------------

The release uses native map, Avatar, Vehicle, HUD and collision resources.
Player input follows stock #1513 `PlayerAvatar.moveVehicle` and
`WGVehicleFilter.notifyInputKeysDown`; because no retail server supplies the
resulting transform stream, the copied 0.8.2 integrator owns the canonical
pose and feeds the native camera, gun, minimap and HUD consumers. Remote
vehicles restore the mature 0.8.2 split: a Python gameplay identity owns
pose/health/collision while a separate `OfflineEntity` owns the #1513 compound
model. The LAN layer applies authoritative poses to that presentation and does
not call the forbidden client-side `Entity.teleport` operation.
Bots run on one elected client; the Python server owns shared HP, shot events,
frags, human team-killer state, elimination, standard base capture, the
15-minute timeout and round reset. Non-standard modes are not implemented.
The bot stack uses the finalized 0.8.2 planner, local driver, reverse-steering
recovery and server macro coordinator. Its #1513 navigation batch is baked
from the real terrain, static collision and water resources for all 41
supported standard maps; player and bot formation slots use the same safe
spawn anchors and ground heights. Human player spotting applies the shared
50/500-metre bounds, exact #1513 moving/still vehicle camouflage, shot penalty,
